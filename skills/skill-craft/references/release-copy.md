# 发布文案写法：README / Release 正文 / CHANGELOG 的中文行文标准

> 提炼自 reduce-ai-zh 技能（通用中文文风规则），聚焦发布场景的子集。本技能自包含，
> 不要求装 reduce-ai-zh；两者可叠加——装了它，任何中文成段文本都按它的完整规则写。

写给模型的两条使用时机：**起草或审校 Release 正文、README、CHANGELOG 之前先读本文件**；
`craft_cli.py check --notes-file` / `release` 的机器腔 lint 是警告级提醒，最终靠这里的手艺过关。

## 硬约束（风格让位于事实）

1. **事实零改动。** 数字、命令、版本号、文件名，有实测就写实测，没实测就写定性
   （"更快"而不是"快 40%"）。一个编出来的数字比十句空话有害——空话读者跳过，假数字读者引用。
2. **术语前后一致。** 同一个东西从头到尾一个名字。"安装器/安装脚本/部署器"来回换，
   读者以为是三个东西。术语轮换是机器腔的典型特征，行内人不这么做。
3. **命令逐字可复制执行。** 不为了简洁砍必要参数，不为了详尽复读三遍。写完自己贴进终端跑一遍。

## README / 发布说明的排版与语气

- **标题不带 emoji**，一个都不带。"🚀 快速开始"是生成式文档的标志。
- badge 最多一行（托管平台、许可证），够用即止。
- 不给术语随手加粗——加粗一多，哪里都不 emphasized。
- 章节按实际需要设，不照搬"简介/特性/安装/使用/路线图/贡献/许可证"全家桶。
  安装说明只出现一次。
- **陈述事实，不做营销。** 这些词删掉后信息量不受损，删：强大、高效、优雅、轻松、
  惊人、卓越、一站式、全方位、端到端、赋能、抓手。
- 不设"为什么选择 X？"式自问自答标题。
- 已知问题就写已知问题，不写"仍在积极开发中"糊过去。
- 路线图要么一两条具体的，要么不写。
- 中文技术文档的语感：直接、可执行、少形容词。"您可以执行以下命令来安装"不如
  "安装："加命令块。读者是来办事的，挡在他和命令之间的每个字都要有理由。

## 行文规则（发布正文场景精选）

- **具体优先于抽象。** 每段至少落在一处具体的东西上：哪个文件、哪条命令、哪个数字。
  自检：整段能原样搬进任何仓库的发布说明，就说明太空，重写。
- **不点题说教。** 改动列表写完就停。禁止"这标志着项目迈入新阶段""综上所述"式收尾——
  读者读完改动自己会得出结论。
- **四字格克制。** "稳定可靠、快速响应、易于维护、扩展性强"这种连排一段最多一组，
  多数场合改散句。
- **对举句式分流。** "不是X，而是Y"：负向项没信息量就删掉只说 Y；是要澄清的误解就
  "是 Y，而非 X"；是真要破的默认假设才保留先破后立。全文两三处封顶。
- **连接词服务逻辑。** 删掉后逻辑变模糊就留，只是语气变平就删。"因此""然而"同段最多各一次。
- **一个观点说一次。** 不"换句话说"，发现重复删掉较空的那句。

## Release 正文五件套（craft_cli 骨架即此结构）

```
改动内容（具体到文件/命令/行为）/ 为什么（根因一两句）/
实测（跑了什么、结果如何；没实测的不写）/ 升级方式（按渠道分别写）/
契约（输出契约是否变更）
```

写"实测"一节时的诚实标准：只在真跑过的项上写具体结果；dry-run 过但没 E2E 的，
写"已 dry-run，未实测线上"——如实标注比漏标强。

## 裁决句

拿不准时回到一句话：**这样写，一个行内人读起来会不会觉得别扭？**
行内人不会数你的连接词，只会觉得"读着舒服"或"一股机器味"。规则为这句话服务，冲突时以它为准。

## 与 lint 的关系

`craft_cli.py` 的机器腔 lint（词表见 `vocabulary.md`）只做提醒不阻断——风格不设硬门禁，
防误伤。lint 命中后不是机械替换（换个词反复用会变成新的机器腔），而是回到上面的规则改写，
通常的解药是**删除**或**落实成具体内容**。
